# 인증 초기 상태·구조 개선 (PR-3) — 대기 구간 제거와 상태 모델 정리

2026-08-03 · 상태: **후보 검토 중 — 확정안 없음** (§6 ADR 의 판단 기준으로 결정) · 선행: PR-1 `fix/idle-auth-ui-guards`, PR-2 세션 판정 개선

> **용어**: 이 문서에서 **후보**는 검토 대상, **현재 기준 유력 후보**는 오늘까지의 근거로 가장
> 앞선 안, **확정안**은 결정된 안을 뜻한다. **이 문서에 확정안은 없다.**

## 1. 배경

웹 클라이언트는 인증 상태를 **아무것도 모르는 채로** 시작한다. 스토어 초기값이 `'idle'` 이고
(`auth-store.ts:16`), 실제 상태는 `/users/me` 응답이 와야 정해진다. 인증 쿠키 3종이 모두
HttpOnly 라 JS 가 읽을 수 없기 때문이다.

브라우저를 다시 연 직후에는 access 쿠키(30분)가 이미 만료돼 있어 복원에 **세 번의 왕복**이 든다.

```
GET /users/me      → 401
POST /auth/web/refresh → 204
GET /users/me      → 200
```

프로덕션 실측(QA 계정, 홈 하드 로드, 개발자 네트워크 환경): 2.4초에 인증 관련 UI 가 그려지고,
4.2초에 첫 401, 5.4초에 갱신 성공, 6.0초에 로그인 상태 확정. **약 3.6초 동안 앱은 로그인 여부를
모른다.** (측정 조건이 사용자 환경과 다를 수 있어 절대값이 아니라 구간 비율로 읽어야 한다.)

**PR-2 를 먼저 하는 이유**: 이 PR 을 먼저 넣으면 힌트로 로그인 화면을 그린 뒤
`AuthSessionBootstrap` 의 현재 로직(401 무조건 종료)이 일시 장애에서 그 화면을 뒤집는다.
PR-1 이 없앤 깜빡임이 더 나쁜 형태로 되살아난다.

## 2. 문제 정의

1. **인증 확인 대기가 공개 트래픽 전체에 부과된다.** 비로그인 방문자도 홈 헤더가 확정될 때까지
   자리표시를 본다.
2. **`idle` 이 두 가지 뜻을 겸한다.** "아직 확인 시작 전"과 "확인 중"이 같은 값이고, 확인이
   실패해 영영 확정되지 않는 경우도 같은 값이다.
3. **소비자마다 대기 처리를 새로 짜야 한다.** 규약이 코드가 아니라 관례로만 존재한다
   (PR-1 에서 손댄 소비자 6곳이 **전부** 어긋나 있었다).
4. **인증 종속 쿼리가 확정될 때까지 잠겨 있다.** `enabled: status === 'authenticated'` 6곳이
   확인 중에 비활성이라, 그 데이터에 의존하는 화면이 잘못된 기본값으로 렌더된다.
5. **임시 방편이 남아 있다.** PR-1 의 대기 상한(`useBoundedAuthStatus`)은 확인이 끝나지 않는
   장애에서 로그인 진입점을 되살리기 위한 것이지 정상 흐름에 있어야 할 코드가 아니다.

## 3. 현재 구조 분석

### 3.1 상태 모델

```ts
// packages/stores/src/auth-store.ts:7-12
status: 'idle' | 'authenticated' | 'unauthenticated';
```

전이는 `setSession`(200)과 `clearSession`(종료 확정) 둘뿐이다. 확인이 401 이 아닌 이유로 실패하면
어느 쪽도 호출되지 않아 `idle` 이 종착점이 된다.

### 3.2 auth_hint 는 존재하지만 서버 쪽에서만 쓰인다

`auth_hint` 는 HMAC 서명된 JWT 로 `typ`·`role`·`exp` 만 담는다(`WebAuthCookieService.java:89-96`,
`middleware.ts:9-13`). rememberMe 면 30일, 아니면 세션 쿠키. HttpOnly 이므로 JS 는 못 읽는다.

**이 토큰은 자격증명이 아니다.** 백엔드 인증 필터는 access 쿠키만 보고
(`JwtAuthenticationFilter.java:72`), CSRF 필터도 access 쿠키만 본다. auth_hint 는 **미들웨어
라우팅 판단에만** 쓰이며 어떤 데이터 접근 권한도 부여하지 않는다(`middleware.ts:119` 주석).

미들웨어 matcher 는 보호 경로에만 걸려 있다.

```ts
// middleware.ts:121-128
matcher: ['/apply/:path*', '/me/:path*', '/manage/:path*', '/admin/:path*']
```

**홈(`/`)과 탐색(`/clubs`)에는 미들웨어가 돌지 않는다.**

### 3.3 렌더 경로와 정적 페이지 현황

루트 레이아웃(`app/layout.tsx`)은 `headers()`·`cookies()`·`dynamic` 을 쓰지 않는다.
빌드 기준 라우트 표의 정적(`○`) 페이지는 **40개**다.

중요한 사실 둘:

- **홈은 이미 동적이다** — `app/(home)/page.tsx:24` 의 `export const dynamic = 'force-dynamic'`
- **헤더를 소유한 것은 `(home)/layout.tsx`** 이고, 탐색 계열은 `ExploreNav` 가 별도 레이아웃에 있다

즉 인증 UI 는 루트가 아니라 **세그먼트 레이아웃**이 소유한다. 이 사실이 후보 평가를 가른다.

(루트 레이아웃에서 요청 헤더를 읽으면 동적화되는 것은 40개 전부가 아니라 **37개**다 —
`robots.txt`·`sitemap.xml`·`favicon.ico` 는 루트 레이아웃을 렌더하지 않는다.)

### 3.4 인증 종속 쿼리 게이트 (6곳)

```
packages/hooks/src/auth.ts:58          useMeQuery
packages/hooks/src/auth.ts:68          useMySessionsQuery
packages/hooks/src/favorites.ts:18     useFavoriteListQuery
packages/hooks/src/favorites.ts:29     useFavoriteIdsQuery
packages/hooks/src/applications.ts:73  내 지원 목록
packages/hooks/src/applications.ts:91  지원 상세 (+ applicationId 조건)
```

게이트 자체에는 정당한 이유가 있다 — 비로그인 401 이 전역 갱신 플로우를 깨우는 것을 막는다.
문제는 `idle` 을 `unauthenticated` 와 같게 취급한다는 점이다. PR-1 에서 부작용 둘이 드러났다.

- **RQ v5 에서 비활성 쿼리는 `isLoading === false`** → `AdminRoleGuard` 가 권한 거부 문구를 먼저 띄웠다
- **찜 목록이 비어 있어 하트 방향이 뒤집힌다** → 이미 찜한 동아리를 누르면 추가가 나가 409 로 실패

대조군: `ManageShell.tsx:160` 은 게이트 없이 쿼리를 쏘고 401 을 API 계층의 갱신에 맡긴다.
로딩 표시가 정상 동작하고 결함이 없다.

### 3.5 PR-1 이 남긴 임시 장치

`app/_lib/useBoundedAuthStatus.ts` — 대기에 30초 상한(복원 예산 10+8+10=28초 위). 소비자 5곳.

## 4. 선행 측정 — 인프라를 늘리기 전에 확인한다

실측 구간을 뜯어보면 **인프라 추가 없이 줄일 수 있는 부분**이 있다.

- **2.4초(요청 시작 전)** — `/users/me` 는 Providers 트리 안쪽 `AuthSessionBootstrap` 의
  `useEffect` 에서야 출발한다. `apiClient` 는 이미 `providers.tsx` 모듈 스코프에 있으므로,
  거기서 프로미스를 띄우고 부트스트랩이 받아쓰면 **요청이 하이드레이션보다 먼저 나간다**(수 줄)
- **왕복 3회** — 콜드 로드에서 access 30분 만료가 사실상 확정적이면 refresh 를 먼저 쳐서 2회로 줄인다

### 4.1 측정 → 설계 결정으로 이어지는 흐름

이 두 가지를 먼저 적용하고 **§11 Success Metrics 3번과 같은 방법으로 재측정**한 뒤, 결과에 따라
아래로 갈린다.

| 재측정 결과 | 다음 단계 |
|---|---|
| 인증 UI 확정까지 **1.5초 이하** | 초기 상태 주입은 **하지 않는다.** 남은 지연은 체감 임계 아래이고, 쿠키·SSR 변경의 비용이 이득을 넘는다. 이 PR 은 §4 + §8 상태 모델 + §9 훅 정리로 축소한다 |
| **1.5초 초과** | §5 후보 비교를 적용한다. 이때 남은 지연의 성격(전 방문자 공통인가, 로그인 사용자만인가)에 따라 §6.3 기준표로 후보를 고른다 |

**임계 1.5초의 근거**: 홈 LCP 이후 헤더가 바뀌면 사용자가 변화를 인지한다. 그 이전이면 첫 인상에
포함돼 "바뀌었다"로 읽히지 않는다. 정확한 값은 재측정 시 실제 LCP 와 비교해 조정한다.

## 5. 초기 상태 주입 — 후보 비교

### 5.1 확정 시점에 대한 정정

초기 판본은 A/B/C 모두 "첫 페인트 확정"으로 적었다. **틀렸다.**

클라이언트가 `document.cookie` 를 읽는 방식(B·C·D·E)은 SSR/프리렌더 HTML 에 반영될 수 없다.
렌더 중 쿠키를 읽어 SSR 결과와 다른 트리를 그리면 하이드레이션 불일치이고, 이 레포는 같은 함정을
이미 겪었다(리듀스드 모션 initial 분기 사례). 따라서 이들의 확정 시점은 **하이드레이션**이다.

진짜 첫 페인트가 필요하면 `<head>` 인라인 스크립트로 `documentElement` 에 표식을 찍고 CSS 로
가르는 테마-플래시 패턴뿐인데, 그건 쿠키든 localStorage 든 동일하게 가능하므로 어떤 후보의 우위도
아니다.

### 5.2 후보 목록

| 후보 | 전달 경로 | 확정 시점 | 정적 페이지 | 변경 범위 | 새 신호 |
|---|---|---|---|---|---|
| **A. 루트 레이아웃 SSR** | 미들웨어 → 요청 헤더 → 루트 `headers()` | SSR | **37개 동적화** | FE only | 없음 |
| **A′. 세그먼트 레이아웃 SSR** | `(home)` 레이아웃에서만 판독 | SSR | **손실 0** (홈은 이미 동적) | FE only | 없음 |
| **B. 미들웨어 미러 쿠키** | 미들웨어가 비-HttpOnly 쿠키 발급 | 하이드레이션 | 유지 | FE only, matcher 전 경로 확장 | 쿠키 +1 |
| **C. 백엔드 미러 쿠키** | `WebAuthCookieService` 에 발급·삭제 추가 | 하이드레이션 | 유지 | FE + BE | 쿠키 +1 |
| **D. 로컬 이력 시드** | `duing:had-session` 을 초기값으로 | 하이드레이션 | 유지 | FE only, 신규 인프라 0 | 없음 |
| **E. auth_hint 를 non-HttpOnly 로** | 기존 쿠키의 HttpOnly 플래그만 해제 | 하이드레이션 | 유지 | BE 1줄 | 없음 |

### 5.3 후보별 채택 근거와 기각 근거

**A** — 정석이다. 서명 검증된 값을 서버가 알고 SSR 에 반영하므로 하이드레이션 불일치가 없다.
기각 근거: 인증 UI 하나를 위해 37개 페이지의 배포 특성을 바꾼다. CDN 캐시 이득이 사라지고 모든
요청이 렌더를 거친다. **A′ 가 같은 이득의 대부분을 0 비용으로 주므로 A 를 고를 이유가 없다.**

**A′** — 문제 정의 1번의 대표 증상(홈 헤더 대기)을 정적 페이지 손실 없이, 서명 검증된 값으로,
SSR 시점에 해소한다. 기각 근거는 아니지만 한계: 정적 라우트에 있는 인증 UI(탐색의 찜 하트, 시설
예약 폼)는 덮지 못한다. 그 범위까지 필요한지가 C/E 를 고를지의 갈림길이다.

**B** — 정적성을 지키면서 서명 검증된 값을 쓸 수 있다. 기각 근거: matcher 를 전 경로로 넓혀야 해
모든 요청에 Edge 미들웨어와 HMAC 검증이 붙는다. C 와 같은 쿠키 추가 비용을 지면서 운영 비용만 더 든다.

**C** — 발급·삭제 시점이 이미 `WebAuthCookieService` 한 자리에 모여 있다. 실제 우위는 정확도가
아니라 **수명 의미론**이다: rememberMe=false 시 브라우저 종료로 자동 소멸, 서버가 정한 만료를
따름, 그 브라우저가 받는 응답으로 삭제. 기각 근거는 아니지만 비용: 쿠키가 4종이 되고 §6.2 의
동기화 규율이 영구히 추가된다.

**D** — 신규 인프라 0. 기각 근거: **만료를 반영하지 못해 30일 지난 세션도 로그인으로 보인다.**
(초기 판본은 "타 기기 로그아웃을 모른다"를 기각 근거로 적었는데, 그건 C 도 마찬가지라 불공정한
비교였다 — `logoutAllSessions` 는 호출한 브라우저의 쿠키만 지운다.) 단독 후보로는 약하지만
**다른 후보의 폴백으로는 유효하다**(§7.2).

**E** — 쿠키 추가 0개 = 동기화 경로 0개. C 의 최대 리스크가 구조적으로 소멸한다.
**리뷰에서 평가가 갈렸고 이 문서는 결론을 내지 않는다.**

| 찬성 근거 | 반대 근거 |
|---|---|
| auth_hint 는 자격증명이 아니다. 백엔드 인증·CSRF 필터 모두 access 쿠키만 본다 | 서명된 토큰을 XSS 가 읽어 **다른 브라우저로 이식**하면 미들웨어 게이트를 통과한다 |
| 미들웨어는 요청 쿠키를 읽으므로 HttpOnly 여부와 무관하게 동작한다 | 게이트 통과는 오늘은 빈 셸뿐이지만, 미래에 미들웨어가 더 하게 되면 전제가 무너진다 |
| 쿠키 추가 0 → "미러와 세션이 어긋난다"는 최대 리스크가 **구조적으로 소멸** | 30일 수명의 읽기 가능한 서명 토큰이 생긴다 |
| XSS 는 이미 사용자 쿠키로 API 를 호출할 수 있어 새 권한이 아니다 | 심층 방어를 자발적으로 한 겹 벗는 변경이다 |

Out of Scope 가 배제한 것은 auth_hint 의 **스키마·서명·수명**이고 HttpOnly 플래그는 거기 없다.
따라서 E 는 배제된 적 없는 후보다.

## 6. Decision Record (ADR)

**이 절은 후보 비교와 판단 기준만 제시한다. 선택은 §7 에서 별도로, 그것도 "현재 기준 유력 후보"
수준으로만 한다.**

### 6.1 두 쿠키(auth_hint + 미러)를 장기적으로 함께 유지하는 비용

- 같은 사실을 두 값이 표현한다 → 어긋날 축이 생긴다. 예: `AUTH_HINT_SECRET` 로테이션 시 서명
  힌트는 무효인데 미러는 유효 → **미들웨어와 화면이 서로 모순되는 판정**을 한다(오늘은 힌트가
  하나라 불가능한 상태다)
- 이름·스코프 관리 부담: B 를 나중에 얹거나 C↔B 를 바꾸면 **같은 이름이 두 스코프로 공존**해
  `document.cookie` 가 스텔 값을 영구히 반환할 수 있다. 서버의 Domain 삭제로는 host-only 잔존본이
  안 지워진다

### 6.2 모든 경로에서 두 쿠키를 동기화하는 비용

`clear()` 호출부는 **요청을 보낸 브라우저에만** Set-Cookie 를 쓴다.

| 경로 | 미러 정리 여부 |
|---|---|
| 로그인 / 갱신 성공 | 발급 (동기화 OK) |
| 그 브라우저의 로그아웃·자격 변경 | 삭제 (동기화 OK) |
| **다른 기기에서 전체 로그아웃·세션 개별 폐기** | 대상 브라우저는 응답을 못 받음 → 잔존 |
| **모바일(Bearer) 앱에서 전체 로그아웃** | `AuthTransport != COOKIE` 라 `clear()` 자체가 호출되지 않음 → 웹 쿠키 4종 전부 생존 |
| refresh 재사용 탐지로 가족 폐기 | 폐기된 정상 기기 쪽 잔존 |
| `AUTH_HINT_SECRET` 로테이션 | 힌트만 무효, 미러 유효 → 모순 |

여섯 경로 중 넷은 서버가 정리할 수 없다. 각 경로마다 "미러도 함께"를 기억해야 하는 규율이
영구적으로 추가된다.

### 6.3 인증 쿠키 증가에 따른 유지보수성

- `WebAuthCookieService.baseCookie()` 는 `httpOnly(true)` 를 하드코딩하고 3종이 전부 이 하나를
  지난다. 여기에 플래그를 뚫으면 **진짜 쿠키의 HttpOnly 가 실수로 꺼질 수 있는 유일한 지점**이
  생긴다. 기존 테스트의 `allSatisfy(... "HttpOnly")` 단언을 느슨하게 고치고 싶어지는 압력도 온다
- `Domain=.duings.com` 쿠키는 `files.duings.com`(R2 이미지 호스트) 요청에도 실려 나간다

### 6.4 향후 확장성 및 운영 복잡도

- **쿠키 속성**: `__Host-` 는 Domain 을 금지하므로 미러에 쓸 수 없다(`api.duings.com` 발급 →
  `duings.com` JS 판독에 `Domain=.duings.com` 필수). `__Secure-` 는 필수. 결과적으로 기존 3종은
  `__Host-`/경로 스코프로 보호되는데 **미러만 모든 `*.duings.com` 에서 읽기·쓰기 가능**하다
- **관측**: 게이트를 힌트로 열면 스텔 신호 부팅마다 401 이 늘어난다. Sentry/PostHog 401 볼륨이
  올라 알림 임계치 재조정이 필요하다
- **폐기 경로(exit path)**: 배포된 쿠키는 사용자 브라우저에 최대 30일 남는다. 되돌리려면 "새로 안
  심기"만으로 부족하고 삭제 응답을 한동안 유지해야 한다. **도입보다 제거가 비싼 결정이다**

## 7. Recommendation (현재 기준)

**확정안이 아니다.** §4 재측정 전이므로 아래는 오늘까지의 근거로 매긴 순서일 뿐이다.

| 순위 | 후보 | 현재 기준 평가 |
|---|---|---|
| 1 | **A′** | 정적 페이지 손실 0, 쿠키 추가 0, 동기화 0, SSR 확정. 문제 정의 1번의 대표 증상을 가장 싸게 덮는다. 한계는 덮는 범위(홈 계열) |
| 2 | **E** | A′ 가 못 덮는 정적 라우트까지 전부 덮으면서 쿠키를 늘리지 않는다. 단 XSS 축의 반대 근거(§5.3)가 해소돼야 한다 |
| 3 | **C** | 기능적으로 충분하나 동기화·제거 비용이 크다. A′ 와 E 가 모두 막혔을 때의 선택지 |
| — | A · B · D | A 는 A′ 에 열위, B 는 C 의 상위 비용, D 는 단독으로는 부족(폴백으로만 유효) |

**현재 기준 가장 유력한 후보는 A′ 이며, 범위가 부족하면 E 를 얹는 조합이다.**
초기 판본이 유력 후보로 적었던 C 는 §6.5 채점에서 3순위로 내려갔다.

## 8. 상태 모델

`checking` 을 3번째 status 값으로 두면 도달 불가이거나(시드가 항상 둘 중 하나로 정해지므로)
`useBoundedAuthStatus` 삭제 근거가 무너진다(확인이 안 끝나는 장애에서 다시 대기 상태가 생김).
그래서 status 는 2값으로 줄이고 확인 여부를 별도 플래그로 뺀다.

```ts
type AuthState = {
  user: User | null;
  status: 'authenticated' | 'unauthenticated';   // 현재 최선의 판단(시드 또는 확정)
  isVerified: boolean;                            // 서버 응답으로 확인됐는가
};
```

### 8.1 불변식 (Invariants)

구현 중 의미가 흔들리지 않도록 세 가지를 못박는다.

1. **`status` 는 현재 최선의 판단이다.** 시드로 세운 값이든 서버로 확인한 값이든, 그 시점에
   앱이 가진 가장 좋은 답이다. "모른다"를 표현하지 않는다.
2. **`isVerified` 는 서버 검증 여부다.** `status` 가 맞는지 틀린지가 아니라, 서버 응답으로
   확인된 값인지만 나타낸다.
3. **소비자는 둘을 혼용하지 않는다.** 화면을 그리는 데는 `status` 만 쓰고, 되돌릴 수 없는
   동작과 세션 종료 처리에는 `isVerified` 를 함께 본다. `isVerified` 로 화면을 가르거나
   `status` 만으로 파괴적 동작을 실행하는 코드는 이 모델 위반이다.

| 값 | 소비자 사용법 |
|---|---|
| `status` | 화면 렌더 — 헤더·가드는 이걸로 그린다 |
| `isVerified` | 되돌릴 수 없는 동작(지원 제출·찜 토글 방향)과 **만료 처리 발동**(§9.1) |

§9.2 의 3단 시드에서 "확인 중 유지" 칸은 이 모델에서 `isVerified=false` + 직전 상태 보존으로
표현한다. `useBoundedAuthStatus` 삭제 조건은 **"시드가 미인증으로 잘못 떨어지는 경로가 없을 때"**
이고, 3단 폴백을 두면 충족된다.

## 9. 낙관적 시드의 공통 전제

**어떤 후보를 고르든** 부팅 시점에 `authenticated` 를 추정하려면 아래가 선행돼야 한다.

### 9.1 소비자 전수 조사가 먼저다 — 특히 만료 핸들러

`SessionExpiryHandler.tsx:28` 의 가드는 `status !== 'authenticated'` 다. 부팅 시 `authenticated`
를 시드하면 **코드를 한 줄도 고치지 않아도** 스텔·위조 신호 하나가 만료 토스트 + 캐시 비움 +
`/login` 강제 이동을 발동시킨다. 지금은 같은 401 사슬이 이 가드에서 조용히 반환된다.

즉 시드의 실패 피해는 "로그인한 것처럼 보이는 화면"이 아니라 **정상 방문자를 로그인 페이지로
튕겨내는 것**이다.

→ 가드를 **`isVerified && status === 'authenticated'`** 로 바꾸고 회귀 테스트로 고정한다.

### 9.2 "신호 없음"을 미인증으로 단정하지 않는다

미러 쿠키(C)는 로그인·갱신 성공 시에만 발급되므로, access 가 아직 유효한 하드 로드는 `Set-Cookie`
없이 200 만 받아 **미러가 없다.** rememberMe 30일 인구에서 이 꼬리는 사실상 무기한이다.

이때 `unauthenticated` 를 시드하면 **미들웨어는 서명된 힌트로 `/me` 를 통과시켰는데 화면은
"로그인이 필요한 페이지예요" 를 렌더**한다(`MeAuthGuard.tsx:19`). 오늘은 `idle` 이라 보이지 않는
화면이며, 이 레포가 기록한 fail-open 원칙과도 반대다.

→ 시드를 3단으로 둔다.

| 신호 | 로컬 이력(`duing:had-session`) | 시드 |
|---|---|---|
| 있음 | — | `authenticated` (`isVerified=false`) |
| 없음 | 없음 | `unauthenticated` — 공개 트래픽 대기 제거 |
| 없음 | 있음 | **확인 중 유지** — 오늘 동작 그대로(오답 방지) |

D 후보가 여기서 폴백으로 재활용된다(`hadSession()` 은 이미 구현돼 있어 추가 비용 0).

### 9.3 role 은 담지 않는다

`/manage` 는 미들웨어가 role 을 보지 않는다(인증 여부만 확인). JS 로 읽히는 role 이 놓이면
`AdminRoleGuard` 를 새 모델로 갈아끼우는 바로 그 작업에서 `meQuery.data?.role` 대신 그 값을 쓰는
"최적화"가 나올 수 있고, 그 순간 `/manage` 계열은 무방비다.

→ 값은 `1` 하나로 고정, 판독은 boolean 만 반환하는 단일 모듈, 그 밖의 `document.cookie` 접근은
lint 로 금지.

### 9.4 서명은 불필요하다 (C·B 의 경우)

미러의 소비자는 자기 자신뿐이고, 자기 자신은 서명 유무와 무관하게 어떤 상태든 만들 수 있다.
(auth_hint 가 서명된 이유는 소비자가 **엣지 미들웨어**여서다. E 는 그 서명을 그대로 쓴다.)

## 10. hooks 구조 개선

게이트 6곳의 조건을 "확정된 미인증이 아닐 때"로 바꾼다. 신호가 로그인으로 보이면 확인을 기다리지
않고 요청한다 — 401 이면 API 계층이 갱신하고, 정말 미인증이면 PR-2 의 만료 경로로 흐른다.
신호가 없으면 여전히 비활성이라 비로그인 트래픽에는 변화가 없다.

**조건 표현의 소유 위치를 정한다.** 소비자가 raw `status` 를 비교하지 않도록 스토어가 셀렉터를
노출하고, 소비자의 직접 비교를 lint 로 막을지 결정한다. 관례로만 남기면 문제 정의 3번이 재발한다.

`useMeQuery` 와 부트스트랩의 `client.users.me()` 직접 호출 중복은 **이 PR 에서 수렴시키지 않는다**
(§16). 부트스트랩 컴포넌트는 유지한다 — PR-2 가 그 컴포넌트에 넣은 계약이 걸려 있다.

## 12. 배포 순서 · 롤백 호환성

C 를 채택하는 경우에만 해당한다(A′·D·E 는 단독 계층이라 순서 의존이 없다).

| 조합 | 관측 동작 |
|---|---|
| BE 먼저 | 무해. 단 기존 로그인 사용자는 다음 갱신까지 미러가 없다(§9.2 폴백이 받는다) |
| FE 먼저 | 미러가 없으므로 §9.2 3단 폴백대로 동작 — 로컬 이력이 있으면 오늘 동작 유지 |
| **BE 만 롤백** | 로그아웃이 미러를 지우지 못한다 → 로그아웃 후 새로고침마다 로그인 화면 + 만료 처리 |

**BE 롤백 위험은 FE 가 `clearSession()` 에서 미러를 직접 지우면 사라진다.** 미러는 비-HttpOnly
이므로 FE 가 **지울 수는 있고 만들 수는 없어**(생성은 서버 응답 필요) 비대칭·안전하다. 레포에
정확한 전례가 있다 — `app/_lib/legacy-auth-cleanup.ts` 의 삭제 문자열.

| 신호 없음을 미인증으로 오독 | §9.2 3단 폴백 | 미들웨어는 통과시킨 `/me` 에서 화면이 "로그인이 필요한 페이지예요"를 띄운다. 기존 로그인 사용자 전원이 다음 갱신까지 이 화면을 본다 |

| 미러만 모든 서브도메인에서 조작 가능 (C·B) | `__Secure-` 필수, 값 고정, 단일 판독 모듈 | 서브도메인 하나가 뚫리면 쿠키 한 줄로 전 사용자를 로그인 페이지로 보낼 수 있다. 데이터 유출은 없으나 가용성 사고다 |
| 쿠키 빌더 오염으로 진짜 쿠키의 HttpOnly 가 꺼짐 (C) | 미러 전용 빌더 분리 + 기존 `allSatisfy` 단언 유지 | access·refresh 가 JS 로 읽히게 된다. **자격증명 유출**로 이어지는 최악의 경로 |

| 서명 토큰이 JS 에 노출 (E) | §5.3 반대 근거 표. 채택 시 "게이트 통과는 보안 경계가 아니다"를 문서·주석에 못박고, 미들웨어가 하는 일이 늘면 재검토 | XSS 가 30일짜리 서명 토큰을 탈취해 다른 브라우저에서 보호 라우트의 셸을 연다. 데이터는 API 가 막지만, 미래에 미들웨어가 서버 렌더에 관여하면 노출로 승격된다 |
| 상태 모델 변경이 소비자 전반에 퍼짐 | PR-2 로 판정이 안정된 뒤 착수. 소비자 목록은 PR-1 에서 확정 | 소비자 일부만 새 모델로 넘어가 `status`/`isVerified` 혼용이 생긴다(§8.1 위반) → 화면과 동작 판정이 갈려 재현 어려운 버그가 남는다 |
