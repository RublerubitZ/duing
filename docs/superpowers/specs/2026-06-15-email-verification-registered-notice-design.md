# 회원가입 인증코드 발송 — 이미 가입된 이메일 안내 (설계서)

- 작성일: 2026-06-15
- 선행 설계: [`2026-06-13-email-verification-design.md`](./2026-06-13-email-verification-design.md)
- 범위: **백엔드 단독** (프론트는 변경 없음 — 사유는 §5)

## 1. 배경 / 문제

회원가입 시 `xxx@daegu.ac.kr` 로 인증코드를 발송한다. 현재 발송 API
(`POST /api/v1/auth/email-verifications`)는 **계정 열거(account enumeration) 방지**를 위해
이미 가입된 이메일이든 미가입이든 **구분 불가능한 동일 응답**(`201 Created` + 만료시각)을 준다.
가입자에게는 실제 코드 메일을 보내지 않는다.

그 결과 **이미 가입한 사용자가 재가입을 시도하면**:

1. 발송은 "성공"처럼 보이고(201),
2. 코드 메일은 영영 오지 않으며,
3. 사용자는 오지 않는 코드를 기다리는 **막다른 길**에 빠진다.

중복 차단 자체는 최종 `signup` 단계의 `existsByEmail` 재검증(409)에서만 노출되어,
사용자는 모든 항목을 다 채우고 제출한 뒤에야 "이미 가입됨"을 알게 된다.

## 2. 결정 (제품 판단)

발송 시점에 "이미 가입된 이메일"임을 사용자에게 **즉시 알린다**. (선택지 A안)

- 트레이드오프: 발송 단계의 계정 열거가 다시 가능해진다. 대구대 동아리 플랫폼 맥락에서
  "이 이메일이 두잉에 가입했는지" 노출 위험은 낮다고 판단하고, **UX(막다른 길 해소)를 우선**한다.
- 완화 장치: **IP 레이트리밋(1분당 5회)** 이 그대로 유지되어 자동화된 열거 탐색 속도를 제한한다.
- 권위(authoritative) 중복 차단은 여전히 `signup` 단계 `existsByEmail` 재검증이 담당한다
  (발송 분기를 바꿔도 약화되지 않는다).

## 3. 백엔드 변경

### 3.1 새 예외

`EmailVerificationException.EmailAlreadyRegisteredException`
- HTTP `409 CONFLICT`, code `EMAIL_ALREADY_REGISTERED`
- 메시지: `이미 가입된 이메일입니다. 로그인 후 이용해주세요.`

### 3.2 `GeneralEmailVerificationService.sendCode`

처리 순서를 다음으로 한다:

```
1. IP 레이트리밋 (assertAndRecordIpRequest)   ← 그대로, 가장 먼저 (열거 속도 제한)
2. existsByEmail → true 면 EmailAlreadyRegisteredException(409) 즉시 throw   ← 신규
3. (미가입만 도달) 코드 생성·해시·upsert(쿨다운 검사)
4. 전역 쿼터 예약 → 메일 발송 → 실패 시 쿼터 복구
5. 만료 정보 응답 반환
```

기존 계정열거-방지용 분기(`alreadyRegistered` 인 경우 발송만 스킵하고 전역 쿼터를
예약·반납하던 코드)는 §2 결정으로 더 이상 의미가 없으므로 제거한다. 관련 주석도
"발송 단계에서 가입 여부를 노출(UX 우선), IP 레이트리밋으로 열거 속도 제한, 권위 중복차단은
signup 단계" 로 갱신한다.

## 4. 테스트 (TDD)

`AuthEmailVerificationTest` 기존 3개 케이스가 옛 설계(열거 방지 동일 응답)를 검증하므로 갱신한다.
먼저 기대값을 새 동작으로 바꿔 **RED** 를 확인한 뒤 구현한다.

- `이미 가입된 이메일은 409 EMAIL_ALREADY_REGISTERED 를 반환하고 메일을 보내지 않는다`
  (기존 "미가입과 같은 201" 케이스 재작성)
- `이미 가입된 이메일은 반복 요청해도 쿨다운(429)이 아니라 항상 409 를 반환한다`
  (existsByEmail 가 쿨다운 검사보다 먼저이므로)
- `전역 발송 한도가 소진돼도 이미 가입된 이메일은 409 를 먼저 반환한다 (미가입은 503)`
  (existsByEmail 가 쿼터 검사보다 먼저임을 문서화)

미가입 정상 흐름·도메인 검증(400)·IP 레이트리밋(429)·confirm 관련 기존 케이스는 그대로 통과해야 한다.

## 5. 프론트엔드 — 변경 없음

프론트는 이 동작을 이미 처리하도록 만들어져 있다(현재는 백엔드가 201 만 주어 비활성 상태):

- `signup/_lib/email-verification.ts` `mapSendError`: `error.status === 409` →
  `"이미 가입된 이메일이에요. 로그인해 주세요."`
- `EmailVerificationField` 가 `errorMessage` 를 렌더한다.
- 회원가입 페이지 하단에 `/login` 링크가 있어 안내가 actionable 하다.
- 기존 테스트 `email-verification.test.ts` 가 `mapSendError(409) → 이미 가입된 이메일 안내` 를 이미 검증한다.

백엔드가 409 를 반환하기 시작하면 이 경로가 그대로 활성화된다.

## 6. Out of Scope

- "인증 진행할 수 없는 아이디"의 다른 사유(레이트리밋 429·전역 한도 503)는 이미 사용자에게
  안내되고 있으므로 변경하지 않는다. 이번 작업은 **"이미 가입됨"** 을 발송 단계에서 노출하는 것에 한정한다.
- 계정 열거 방지 설계를 발송 외 다른 엔드포인트(로그인·비밀번호 재설정 등)로 확장/축소하지 않는다.
- 프론트 UI/문구 재디자인, 로그인 링크를 에러 메시지 안에 인라인으로 넣는 작업은 하지 않는다.
- 마이그레이션·스키마 변경 없음.
