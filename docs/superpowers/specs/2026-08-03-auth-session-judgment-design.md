# 인증 상태 판정·세션 만료 처리 개선 (PR-2) — 종료 판정의 단일 출처 복원

2026-08-03 · 상태: **설계 확정 (구현 전)** · 선행: PR-1 `fix/idle-auth-ui-guards`

## 1. 배경

웹 인증은 HttpOnly 쿠키 3종(access 30분 · refresh 30일 · auth_hint 30일)으로 돌아간다. access 가
만료되면 `afterResponse` 훅이 `/auth/web/refresh` 를 한 번 시도하고, 성공하면 원 요청을 재시도한다
(`client.ts:914-949`). 이 구조 덕분에 사용자는 30분마다 로그아웃되지 않는다.

PR-1 은 이 복원이 진행되는 동안(`status: 'idle'`) 화면이 "확인 중"을 "로그아웃"으로 표시하던
문제를 고쳤다. 그 과정에서 **화면 아래쪽, 판정 계층에 별도의 결함이 있다**는 것이 드러났다.
PR-1 은 UI 소비자만 건드리기로 범위를 그었고, 판정 계층은 이 문서가 다룬다.

### 1.1 설계 원칙 — 종료 판정의 단일 출처는 `SessionExpiryHandler` 다

이 문서의 모든 결정은 아래 한 문장에서 나온다.

> **세션이 끝났다고 판정하는 코드는 앱 전체에 한 곳,
> `SessionExpiryHandler` 의 사이드 채널 구독부에만 존재한다.**

API 계층은 이미 그 계약을 갖고 있다 — "세션 종료는 `notifyUnauthorized` 로 통지하고, 예외로
던지는 401 은 그저 이 요청이 401 이었다는 뜻"(`client.ts:868` 주석). 지금 문제는 이 계약을 쓰지
않는 두 번째 판정자(`AuthSessionBootstrap`)가 생겼고, 그 판정자가 만료와 일시 장애를 구분하지
못한다는 것이다. 이 PR 은 새 규칙을 만드는 게 아니라 **이미 있는 규칙으로 되돌린다.**

## 2. 문제 정의

1. **일시 장애가 로그아웃으로 처리된다.** 조건은 좁다 — **access 만료로 401 이 난 요청에서
   갱신이 401/404 가 아닌 이유(403 · 5xx · 타임아웃 · 오프라인)로 실패할 때**다. 이때 사용자는
   로그아웃되지만 세션은 서버에 살아 있어, 다음 페이지 로드에서 다시 로그인 상태가 된다.
   (`/users/me` 자체가 5xx·네트워크로 실패하는 경우는 401 분기를 타지 않아 로그아웃되지 않는다.)
2. **확정된 만료가 부팅 중에는 상태에 기록되지 않는다.** 브라우저를 다시 연 직후 세션이 진짜
   만료돼 있으면 그 사실이 어디에도 남지 않아, 이후 화면이 만료를 모른 채 동작한다.
3. **종료 판정이 두 곳에 흩어져 있다**(§1.1 원칙 위반). 두 규칙이 어긋나는 지점이 위 1·2 다.
4. **만료 신호가 등록 순서에 의존한다.** 알림 채널이 슬롯 하나뿐이라, 핸들러가 등록되기 전에
   도착한 신호는 사라진다.

## 3. 현재 구조 분석

### 3.1 세션 종료 신호는 두 채널로 흐른다

| 채널 | 무엇을 나르는가 | 발화 조건 |
|---|---|---|
| throw (반환 채널) | "이 **요청**이 401 이었다" | 모든 401 |
| `notifyUnauthorized` (사이드 채널) | "**세션**이 확정 종료됐다" | 쿠키 모드에서 refresh 가 401/404 로 답했을 때 (`client.ts:881-883`) |

Bearer(모바일) 모드는 규칙이 다르다 — Authorization 헤더가 붙은 모든 401 에서 발화하고
로그아웃 요청만 제외한다(`client.ts:954-957`). 이 문서는 쿠키 모드만 다룬다.

### 3.2 refresh 실패는 사유별로 분류된다 — 호출자에게 도달하기 전까지는

`client.ts:872-889` 의 갱신 실행기는 응답을 네 갈래로 나누고, 조율기가 다섯 번째 값을 더한다.

| 값 | 만든 곳 | 뜻 | 사이드 채널 |
|---|---|---|---|
| `refreshed` | 실행기 (204) | 갱신 성공 | — |
| `session-expired` | 실행기 (401·404) | 복구 불가 종료 | 발화 |
| `unavailable` | 실행기 (그 외 상태코드 · 예외) | 일시 장애 | 침묵 |
| `skipped` | **조율기** (`refresh-coordinator.ts:37`) | 다른 탭이 10초 내 갱신했음 | 침묵 |

`client.ts:934` 는 `skipped` 를 `refreshed` 와 동일 취급해 원 요청을 재시도한다(→ §9).

분류는 `client.ts:949` 에서 버려진다. `session-expired` 와 `unavailable` 모두 훅이 그냥 반환하고,
ky 가 **원본 401 을 그대로 표면화**한다.

**실측 (실제 백엔드 401 봉투로 5가지 실패를 재현):**

```
refresh 401 (진짜 만료) | notify=1 | ApiError status=401 code=undefined message="인증이 필요합니다."
refresh 403            | notify=0 | ApiError status=401 code=undefined message="인증이 필요합니다."
refresh 500            | notify=0 | ApiError status=401 code=undefined message="인증이 필요합니다."
refresh 503            | notify=0 | ApiError status=401 code=undefined message="인증이 필요합니다."
refresh 네트워크 오류    | notify=0 | ApiError status=401 code=undefined message="인증이 필요합니다."
```

다섯 경우의 예외 객체가 **완전히 동일하다**. message 는 원 요청의 응답 본문이고 `code` 는 백엔드가
인증 401 에 코드를 붙이지 않아 `@JsonInclude(NON_NULL)` 로 생략된다
(`JwtAuthenticationEntryPoint.java:41`). 즉 **호출자는 반환 채널만으로는 만료와 일시 장애를 구분할
수 없다.** 구분은 사이드 채널에만 있다.

이 계약은 기존 테스트에도 박제돼 있다. `authRefresh.test.ts:70`(진짜 만료)과 `:94`(5xx) 두
테스트가 **똑같이 `rejects.toMatchObject({ status: 401 })`** 을 단언하고, 차이는
`unauthorizedHandler` 호출 여부뿐이다.

### 3.3 두 소비자가 서로 다른 계약을 쓴다

- **`SessionExpiryHandler.tsx:24-40`** — 사이드 채널을 구독한다(계약대로). 그러나 `:28` 에서
  `status !== 'authenticated'` 면 즉시 반환한다. 콜드 부팅 중 status 는 항상 `idle` 이므로
  **부팅 중 확정된 만료는 여기서 소멸한다.**
- **`AuthSessionBootstrap.tsx:75`** — 반환 채널의 401 을 세션 종료로 읽는다. 사유를 구분하지
  않으므로 §3.2 표의 다섯 경우가 **전부 로그아웃**이 된다.

두 결함은 맞물려 있다. 사이드 채널이 부팅 중에 꺼져 있으니 부트스트랩이 "401 이면 만료"라는
자기 규칙을 갖게 됐고, 그 규칙이 일시 장애까지 만료로 오판한다.

### 3.4 사이드 채널은 예외보다 먼저 도착한다 (측정으로 확인)

```
refresh 401(진짜 만료) → ['notify', 'reject']    동시 요청 3건에서도 notify 는 1회, 항상 첫 번째
refresh 503(일시 장애) → ['reject']              사이드 채널 침묵
```

`notifyUnauthorized()` 는 훅이 await 하는 갱신 실행기 안에서 호출되고(`client.ts:882`), 원 401 은
그 뒤에 표면화된다(`:949`). zustand `setState` 는 동기이므로, **핸들러가 스토어를 내린 뒤에야
호출자의 `.catch()` 가 실행된다.**

주의: 이 안전성은 형제 컴포넌트의 마운트 순서 덕분이 **아니다**. `providers.tsx:73-74` 는
`AuthSessionBootstrap` 을 `SessionExpiryHandler` 보다 **먼저** 마운트하므로 순서상으로는 오히려
불리하다. 실제 근거는 React 커밋 페이즈가 한 태스크 안에서 끝나 등록이 어떤 비동기 콜백보다 먼저
완료된다는 점이다(StrictMode 이중 호출 포함 실측 유실 0). 배치가 바뀌면 이 근거는 사라진다.

### 3.5 알림 채널은 슬롯 하나에 버퍼가 없다

`unauthorized-context.ts:7-14` 는 핸들러 하나를 전역 변수에 담고, 등록 전에 도착한 알림은 버린다.

### 3.6 백엔드는 이미 올바르게 동작한다 (변경 대상 아님)

- 쿠키 인증 요청의 401 은 access 쿠키만 지운다 — `JwtAuthenticationEntryPoint.java:36` (#806).
  Bearer 요청에는 적용되지 않는다(`:35` 의 transport 가드)
- refresh 회전 실패(만료·폐기·재사용 탐지)는 쿠키 3종을 함께 지운다 — `AuthController.java:167`
- `WebAuthCookieService.issue()/clear()` 가 3종 발급·삭제의 유일 지점이다

서버는 "만료"와 "일시 장애"를 정확히 구분해 응답한다. 문제는 전부 클라이언트 판정에 있다.

## 4. 원인 분석

한 문장으로: **API 계층이 정한 계약(§1.1)을 소비자 하나가 쓰지 않고, 그 소비자가 쓰려 해도 채널이
부팅 시점에 닫혀 있다.**

| 층 | 책임 | 현재 상태 |
|---|---|---|
| 갱신 실행기 (`client.ts:872-889`) | 실패 사유 분류 | **정상** — 네 갈래로 정확히 나눈다 |
| 조율기 (`refresh-coordinator.ts`) | 사이클당 1회 실행 | 실행기 값 + `skipped` 를 반환한다 |
| afterResponse 훅 (`client.ts:933-949`) | 재시도 or 표면화 | 분류를 버린다(의도된 계약) |
| 사이드 채널 (`unauthorized-context.ts`) | 종료 통지 | 유실 가능 구조 |
| `SessionExpiryHandler` | 종료 처리 | 부팅 중 신호를 버린다 |
| `AuthSessionBootstrap` | 세션 복원 | 종료를 자체 판정한다(오판의 출처) |

## 5. 설계안 비교

네 안을 같은 깊이로 검토했다. 채택 근거와 기각 근거를 함께 남긴다.

### 5.1 A. 예외에 구분 코드를 실어 보낸다

`client.ts:949` 에서 `outcome === 'session-expired'` 일 때 구분 코드를 단 `ApiError` 를 던진다.
소비자는 `code` 로 분기한다.

- **채택했다면 얻는 것**: 명시적이다. 순서 의존이 없다. 새 호출자도 자동으로 올바르게 동작한다.
  사이드 채널을 구독하지 않는 코드도 구분할 수 있어 결합이 느슨하다.
- **기각 근거**: **같은 사실이 두 채널로 흐른다(계약 이중화).** 사이드 채널이 이미 "세션 종료"를
  나르는데 예외에도 같은 사실을 실으면 진실의 출처가 둘이 된다. 두 채널이 어긋나는 날 —
  예컨대 한쪽만 갱신하는 변경이 들어올 때 — 어느 쪽이 맞는지 판단할 근거가 없어진다.
  §1.1 원칙("판정은 한 곳")과 정면으로 어긋나는 방향이다.
- **기각 근거로 쓰지 않은 것**: 테스트 계약 갱신 비용은 B 도 동일하다. `packages/api` 의 공개
  계약 변경 비용도 지금은 크지 않다(`apps/` 에는 web 하나뿐, RN 은 아직 없다). 이 둘을 A 의
  감점으로 쓰면 비교가 불공정해진다.

### 5.2 B. 기존 사이드 채널을 복구한다 — **채택**

`SessionExpiryHandler` 의 조기 반환 조건을 고쳐 부팅 중 만료도 받게 하고, 부트스트랩은 401 을
스스로 해석하지 않는다. 종료 여부는 catch 시점의 스토어 상태로 읽는다.

- **채택 근거**: 새 계약을 만들지 않는다. 채널이 원래 그 용도로 설계돼 있고 §1.1 원칙을 그대로
  복원한다. 문제 정의 2번(부팅 중 만료 무기록)도 같은 변경으로 닫힌다. `packages/api` 의 공개
  계약이 바뀌지 않아 영향 범위가 앱 계층에 머문다.
- **약점**: 사이드 채널이 예외보다 먼저 도착한다는 순서에 의존한다. 지금은 성립하지만(§3.4)
  코드에 드러나 있지 않다 → §6.3 채널 버퍼링으로 구조화해 이 약점을 없앤다.

### 5.3 C. 스토어가 종료 이벤트를 소유한다

핸들러 등록을 앱 부팅 모듈 스코프로 올려 스토어 전이만 수행하고, 안내·이동은 전이 구독으로 옮긴다.

- **채택했다면 얻는 것**: 마운트 순서 의존이 원천 제거된다. 판정(스토어)과 표현(UI)의 책임 분리가
  가장 깨끗하다. B 의 상위 호환이다.
- **기각 근거**: 의도적 로그아웃도 같은 전이를 만들므로 스토어에 전이 사유 필드가 필요하고,
  핸들러 슬롯이 하나뿐이라 `SessionExpiryHandler` 의 등록을 걷어내는 재배치가 따라온다.
  지금 고치려는 결함(조건문 하나 + 자체 판정 하나)에 비해 변경 표면이 과하다. **B 를 먼저 하고
  필요해지면 C 로 승격**하는 순서가 맞다.

### 5.4 D. 인증 상태 머신 도입

- **기각 근거**: 지금 문제는 전이가 복잡해서가 아니라 전이 하나가 잘못된 조건문에 막혀서다.
  상태는 3값이고 전이 경로도 명확하다. 머신을 도입하면 같은 버그를 더 많은 코드로 옮겨 담게 된다.

## 6. 채택안 — B + 채널 버퍼링

§6.1·§6.2 가 본체이고, §6.3 은 순서 의존을 구조로 못박는 보강이다(현재도 유실은 없다).

### 6.1 종료 판정을 `SessionExpiryHandler` 로 일원화한다

조기 반환을 "이미 종료가 확정된 경우"로 좁히고, 부팅 중(`idle`)에 도착한 만료도 받아 상태를 내린다.

**부수효과는 반드시 분기한다.** 현재 핸들러는 조기 반환 뒤에 여섯 가지를 한다 —
`setState` · `client.auth.logout()` · `clearSession()` · `queryClient.clear()` · 토스트 ·
`router.push`. 가드를 그냥 열면 **익명 방문자의 모든 페이지 로드마다** 다음이 실행된다:
익명 방문 → `/users/me` 401 → refresh(쿠키 없음) 401 → 알림 발화.

| 부수효과 | 쓰던 중 끊김(직전 authenticated) | 부팅 중·익명 |
|---|---|---|
| `setState(unauthenticated)` + `clearSession()` | 실행 | 실행 |
| `client.auth.logout()` | 실행 | **하지 않음** — 공개 트래픽 전체에 요청 +1 이 된다 |
| `queryClient.clear()` | 실행 | **하지 않음** — 진행 중인 공개 쿼리 캐시까지 날린다 |
| 만료 토스트 · `/login` 이동 | 실행 | 하지 않음 |

**안내 게이트의 술어**: "직전 상태가 `authenticated`" 를 그대로 쓰면 PR-3 에서 의미가 달라진다
(힌트로 `authenticated` 를 시드하면 부팅 직후에도 참이 되어 토스트·이동이 터진다). 이 PR 에서는
인메모리 직전 상태로 구현하되, **술어의 의미를 "이 브라우저에서 세션이 살아 있었는가"로 정의**하고
PR-3 가 구현만 교체하도록 남긴다.

### 6.2 부트스트랩은 401 을 해석하지 않는다

catch 시점에 스토어가 이미 종료로 확정됐으면 처리가 끝난 것이고, 아직 아니면 갱신이 일시 장애로
실패했을 뿐 세션은 살아 있다 → 기존 "세션을 확인하지 못했습니다 + 다시 시도" 경로로 흐른다.

**불변식**: 종료 확정은 **동기 `setState` 로 먼저 기록한다**(`clearSession()` 은 async 라 catch
보다 늦을 수 있다). 현재 코드가 그렇게 돼 있지만 이유가 "중복 토스트 방지"로만 적혀 있어, 둘을
합치는 정리가 들어오면 이 계약이 조용히 깨진다. 테스트로 고정한다(§8.2).

### 6.3 사이드 채널에 보류 플래그를 둔다

등록 전에 도착한 알림을 버리지 않고 등록 시점에 흘린다. 알림은 갱신 사이클당 1회라 큐가 아니라
불리언 하나면 충분하다.

## 8. 테스트 전략

계약 테스트와 통합 테스트의 경계를 렌더 구성으로 가른다 — **단독 렌더는 그 단위의 계약**,
**함께 렌더는 두 단위가 맞물린 결과**를 검증한다.

### 8.1 단독 렌더 — 각 단위의 계약

**`packages/api` (컴포넌트 없음)**
- 보류: 핸들러 미등록 상태에서 종료가 발생해도 등록 시점에 1회 전달된다
- 등록된 핸들러가 있으면 즉시 전달되고 보류가 남지 않는다
- 발화 매트릭스: refresh 401/404 만 발화, 403·5xx·네트워크는 침묵
- 사이드 채널이 예외보다 먼저 도착한다(순서 회귀 테스트)

**`AuthSessionBootstrap` 단독**
- `/users/me` 200 → 세션 복원
- **401 이 와도 스스로 세션을 끝내지 않는다** — 스토어가 `idle` 에 머문다.
  (이 PR 의 핵심 계약 변경. 이전에는 단독으로 `unauthenticated` 로 갔다)
- 비-401 실패(5xx·네트워크) → 확인 실패 안내 + 다시 시도, 세션 유지
- "다시 시도" 후 성공 → 세션 복원

**`SessionExpiryHandler` 단독**
- 알림 수신 시 직전 상태별 부수효과 분기(§6.1 표)가 그대로 나온다
- 이미 `unauthenticated` 면 중복 처리하지 않는다

### 8.2 함께 렌더 — 통합

| 시나리오 | 기대 |
|---|---|
| refresh 401 · 직전 authenticated | 미인증 확정 + 만료 토스트 + `/login?next=` 이동 + 캐시 비움 + 서버 로그아웃 호출 |
| refresh 401 · 부팅 중(idle) | 미인증 확정. **토스트·이동 없음 · `logout` 호출 없음 · `queryClient.clear()` 없음** |
| refresh 503 / 네트워크 오류 | **세션 유지**(idle), 확인 실패 안내 + 다시 시도 |
| 동시 401 여러 건 | 토스트·이동 각 1회 |
| 종료 확정 직후(비동기 완료 전) | 스토어가 이미 `unauthenticated` (§6.2 불변식) |

**회귀 확인 방식**: 각 픽스를 되돌렸을 때 해당 테스트가 실제로 실패하는지 확인한다(PR-1 과 동일).

## 9. Known Limitation — `skipped` 창의 세션 폐기 오분류

**이 PR 이 닫지 못하는 결함이다. 후속에서 반드시 다뤄야 한다.**

조율기는 다른 탭이 10초 내 갱신했으면 실행을 생략하고 `skipped` 를 반환하며
(`refresh-coordinator.ts:37`), 훅은 이를 `refreshed` 와 같게 보고 원 요청을 재시도한다
(`client.ts:934`). 재시도가 다시 401 이어도 bare ky 는 훅을 다시 타지 않아 **사이드 채널이 울리지
않는다.**

```
다른 탭이 10초 내 갱신 성공
  → 그 사이 서버에서 세션 폐기(관리자 강제 로그아웃 · refresh 재사용 탐지 · 타 기기 전체 로그아웃)
  → 401 → skipped → 재시도 401 → notify 없음
```

§6.2 의 규칙("catch 시점 스토어가 종료가 아니면 일시 장애")은 이 경우를 **일시 장애로 오판**하고
"로그인 상태는 유지됩니다"를 안내한다. 창은 10초 이하로 좁지만 하필 **보안 민감 경로**다.

- **현재 코드는 우연히 맞다** — `AuthSessionBootstrap.tsx:75` 의 무조건 401→종료가 이 케이스를
  올바르게 처리한다. 즉 이 PR 은 이 경로에 한해 **한 걸음 후퇴한다.**
- **후속 처리 방향**: `skipped` 후 재시도가 다시 401 이면 스킵 캐시를 무시하고 갱신을 한 번 강제
  실행한다. `client.ts` 변경이라 이 PR 의 "앱 계층만" 범위를 넘는다.
- **후속 전까지의 노출**: 10초 창 × 서버측 폐기 발생 시점의 교집합. 발생 시 사용자는 만료 안내
  대신 재시도 안내를 보고, 다음 요청에서 정상 만료 처리로 흐른다(세션이 살아나지는 않는다).

- **`skipped` 경로의 세션 폐기 오분류** — §9 Known Limitation. `client.ts` 변경이 필요해 별도 후속
- **부팅 중 만료에 대한 사용자 안내** — 이 PR 은 상태 기록까지만 한다. 안내가 필요한지는
  PR-3 에서 화면이 로그인 상태로 그려지게 된 뒤에 다시 판단한다
- **백엔드 인증 로직** — 만료 판정·쿠키 정리는 이미 정확하다(#806 로 검증)

- **네트워크 복구 시 자동 재시도(온라인 이벤트 구독)** — 필요해지면 별도 설계
