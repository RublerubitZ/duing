# Nullable API 계약 가이드 — `200 + null` / `404` / `403` 판단 기준

2026-08-03 · 상태: 기준 확정 (선례 1건 반영 완료)

## 배경

멤버십 조회(`GET /clubs/{clubId}/membership`)가 "이 동아리의 멤버인가"를 묻는 판정 API 인데
멤버가 아니라는 답을 **403** 으로 돌려주고 있었다. 로그인한 사용자가 가입하지 않은 동아리를 열
때마다 정상 탐색이 거부로 기록돼 서버 로그에 경고가 쌓였고, 클라이언트는 정상 흐름을 오류
처리에서 조립해야 했다. 그 결과 접근 가드의 리다이렉트 분기가 조용히 죽어 있는데도 아무도
눈치채지 못했다(#816 에서 발견·수정).

이 문제를 고치면서 레포에 두 가지가 처음 들어왔다.

- **응답 형태**: `200 + data:null` — "없음도 정상 결과" (#817)
- **처리 경로**: `unwrapNullable` / `jsonOkNullable` — 빈 결과를 오류로 바꾸지 않는 언래퍼 (#816)

기준이 문서로 남지 않으면 다음 사람은 셋 중 하나를 한다. 아무 조회에나 nullable 을 퍼뜨리거나,
존재를 몰라 403 을 또 쓰거나, `unwrap` / `unwrapNullable` 중 아무거나 고른다. **계약 일관성은
문서가 없으면 첫 사례를 따라 굳는다.**

## 현황 (2026-08-03 실측)

- 도메인 예외 상태코드 분포: `400` 86 · `409` 74 · **`404` 41** · **`403` 14** · 기타 소수
- `ApiResponse.success(null)` 을 명시적으로 호출하는 곳: **0** — 멤버십 조회가 유일한 선례이며
  `.map(...).orElse(null)` 형태로 조립한다

즉 이 문서는 대규모 정리가 아니라 **선례 1건을 기준으로 승격**하는 것이다.

## 결정 사항

### 응답 표현 선택 기준

먼저 **"호출자가 무엇을 물었는가"** 를 정한다. 자원을 지목한 것인지, 상태를 물은 것인지가 갈림길이다.

| 표현 | 언제 | 판단 근거 |
|---|---|---|
| **`200 + data:null`** | 호출자가 **분기 판단을 하려고** 묻는 술어 조회. 호출 시점에 답을 모르는 것이 정상이고, "없음"도 예상된 결과일 때 | 예상된 결과를 오류 채널로 보내면 호출자가 정상 흐름을 `catch` 에서 조립하게 된다 |
| **`404`** | 호출자가 **자원을 지목**했는데 그 자원이 없을 때 | 자원 지향의 기본값. 단 "없음"과 "권한 없음"이 한 코드로 합쳐져 호출자가 구분하지 못하게 되는 경우는 피한다 |
| **`403`** | **실제 접근 거부**. 보호할 데이터가 있고 호출자가 그것을 요구했을 때 | 403 을 정상 상태에도 쓰면 진짜 권한 위반과 로그에서 구분할 수 없어진다 |

### 결정 흐름

1. 이 호출은 **자원을 달라는 것인가, 상태를 묻는 것인가?**
   - 상태를 묻는다 → **2**
   - 자원을 달라고 한다 → **3**
2. "아니오"가 **호출자가 예상하는 정상 답**인가?
   - 그렇다 → **`200 + null`**
   - 아니다(없으면 그 자체로 비정상) → **3**
3. 호출자에게 이 자원을 볼 자격이 있는가?
   - 없다 → **`403`**
   - 있는데 자원이 없다 → **`404`**
   - 자격 없음과 없음을 구분시키면 자원 식별자를 훑을 수 있게 되는가 → **존재 은닉**: 둘을 같은 응답으로 수렴

### 존재 은닉 규칙

없는 자원과 볼 수 없는 자원의 응답이 다르면, 식별자를 바꿔가며 호출해 무엇이 존재하는지 알아낼 수
있다. 다음 중 하나라도 해당하면 두 경우를 같은 응답으로 맞춘다.

- 식별자가 연속적이거나 추측 가능하다(자동 증가 id 등)
- 존재 여부 자체가 알려지면 안 되는 자원이다(비공개·심사 중·타 조직 소유)

수렴 방향은 위 표를 따른다 — 술어 조회면 `200 + null`, 자원 조회면 `404`.

### 클라이언트 언래퍼 선택 (`unwrap` vs `unwrapNullable`)

- **기본은 `unwrap`** 이다. 빈 본문은 사고이므로 오류로 올리는 것이 맞다.
- **`unwrapNullable` 은 서버가 `data:null` 을 명시적으로 약속한 엔드포인트에만** 쓴다.
  판단 기준은 취향이 아니라 **서버 문서**다 — 해당 API 의 Swagger 에 "멤버가 아니면 data 가 null"
  같은 문구가 있는가. 없으면 쓰지 않는다.
- `unwrapNullable` 도 **봉투 자체가 없는 경우**(본문이 통째로 빈 응답)는 여전히 오류로 처리한다.
  서버가 의도적으로 내린 `data:null` 과 응답이 깨진 것은 다른 사건이다.

한 줄 요약: **nullable 은 계약이 그렇게 정의된 곳에만 따라 붙는다. 클라이언트가 먼저 정하지 않는다.**

## 기존 API 역채점

규칙이 현실과 맞는지 확인한다. **기존 API 다수를 위반으로 판정하는 규칙이라면 규칙이 틀린 것이다.**

| 엔드포인트 | 현재 | 판정 |
|---|---|---|
| `GET /clubs/{id}/membership` (비멤버) | `200 + null` | ✅ 술어 조회 → 표 1행 |
| `GET /clubs/{id}/membership` (비 ACTIVE 동아리 멤버) | `403` + 상태별 안내 | ✅ 실제 접근 거부. 안내 문구를 클라이언트가 그대로 노출 |
| `GET /clubs/{id}` (없는 동아리) | `404` | ✅ 자원 지목 |
| `GET /clubs/{id}/notices` (비멤버) | `403` | ✅ 보호할 데이터가 있음 |
| `GET /clubs/{id}/members/{memberId}/phone` | `404` (타 동아리 id·탈퇴 회원 구분 없음) | ✅ 존재 은닉 명시 적용 사례 |
| `GET /me/clubs` (가입 동아리 없음) | `200 + []` | ✅ 빈 목록은 `404` 가 아니다 |

**위반으로 판정되는 기존 API 는 나오지 않았다.** 규칙은 현재 관행을 성문화한 것이며, 바꾸는 것은
"판정 조회에 403 을 쓰지 않는다" 한 가지뿐이다.

## 적용 범위

- **신규 조회 API**: 설계 시 위 결정 흐름을 따른다
- **기존 API**: 일괄 정리하지 않는다. 역채점 결과 위반이 없고, 계약 변경은 배포 조율 비용을 동반한다
- **`200 + null` 을 새로 도입할 때**: Swagger 에 반드시 명시한다. 문서에 없는 nullable 은 클라이언트가
  알 방법이 없고, `unwrapNullable` 선택 기준 자체가 무너진다

## 미해결 (별건)

- **생성 타입의 역할** — `packages/api/src/generated/schema.d.ts` 는 공개 진입점으로 열려 있지만
  import 하는 코드가 **0곳**이다. 계약 문서 이상의 역할을 하지 못하고 있고, 재생성마다
  `@AssertTrue` 파생 필드의 나열 순서가 흔들려 순서-only diff 가 계속 발생한다. 이 생성물을
  실제 타입 소스로 승격할지, 문서로만 둘지는 이 문서의 범위 밖이다.

## Out of Scope

- 기존 API 의 상태코드 일괄 정리
- 미인증 `403` → `401` 정리 (별도 설계 — refresh·전역 로그아웃 흐름에 영향)
- `4xx` 전반의 코드 체계(`400` / `409` / `422` 구분 기준) — 이 문서는 "없음·거부" 축만 다룬다
- 오류 응답 본문 스키마(`code` 필드 체계)
- 페이지네이션·목록 응답 규약
