# 외부 폼 모집(EXTERNAL) 모드 & 가입 코드 회원 초대 — 스펙 v2

외부 폼(구글폼·네이버폼)은 단순 "URL 입력 옵션"이 아니라 **하나의 모집 모드**다.
지원서를 두잉에서 관리하지 않고, **모집 종료 후** 가입 코드로 합격자를 등록한다:

```
외부 모집 → 모집 종료 → 합격자 선정 → 가입 코드 생성 → 학생 가입 요청 → 운영진 승인 → 회원 등록
```

v1(가입 코드 1차 릴리스, #848~#854) 대비 변경: 코드 귀속을 Club → **Recruitment** 로,
발급 시점을 모집 OPEN 중 → **CLOSED 후** 로 전환하고, EXTERNAL 을 작성·관리 UX 전반의 모드로 승격한다.

---

## 1. 모집 작성 — EXTERNAL 모드 UX

### 1.1 전환 확인 다이얼로그

지원 방식에서 "외부 폼" 선택 시 즉시 전환하지 않고 확인 다이얼로그를 먼저 띄운다:

- 안내 항목: 두잉 지원서 미사용 / 지원서 질문 사용 불가 / 안내문 사용 불가 / 면접 단계 사용 불가 /
  지원자 수 공개 사용 불가 / 가입 코드로 회원을 등록(운영진 승인으로 확정)
- 회원 등록 절차(§7 카드와 동일 플로우) 표시
- [취소] → INTERNAL(자체 폼) 유지 / [확인하고 전환] → EXTERNAL 전환
- **확인 시점에 내부 전용 값 즉시 초기화**: 안내문·지원서 질문·면접 진행·지원자 수 공개 —
  저장 후 400 을 보는 UX 가 아니라 전환 순간 정리한다 (BE 검증은 방어선으로 유지)
- 접근성: 다이얼로그 포커스 트랩·Escape 닫힘(=취소)·버튼 키보드 내비 유지

### 1.2 EXTERNAL 전용 작성 화면

단순 disabled 가 아니라 화면 구성을 바꾼다:

- **표시**: 모집 설정(제목·기간·정원·기수 등 공통), 외부 폼 URL(§3 검증), 회원 등록 안내 카드(§7)
- **숨김**: 안내문, 지원서 질문, 면접 진행, 지원자 수 공개 — 섹션 자체를 렌더하지 않는다.
  구조상 숨기기 어려운 요소만 "외부 폼 모집에서는 사용할 수 없습니다." 안내로 대체
- BE 도 동일 정책 강제(§2) — FE 숨김은 UX, BE 검증이 경계

## 2. BE — EXTERNAL 모집 제약

`applicationMode = EXTERNAL` 인 모집의 **생성** 시 (수정 경로는 의도적으로 미강제 — 내부 전용 값이 남은
레거시 EXTERNAL 모집이 제목만 고쳐도 400 이 되는 것을 막기 위함. FE 는 수정 모드에서 값을 그대로 왕복한다.
⚠️ 후속에서 update 검증을 추가하려면 레거시 값 정리 배치 + FE 왕복 정책 재검토를 반드시 동반할 것):

- `questions`/`questionItems` 비어 있어야 함 (기존 유지)
- `useInterview = false` 강제 — true 요청 시 400
- `showApplicantCount = false` 강제 — true 요청 시 400
- 안내문(작성 폼의 안내문에 해당하는 필드 — 구현 시 실제 필드 확인)은 EXTERNAL 에서 거부(400)
- `externalFormUrl` 필수 + §3 화이트리스트 검증
- INTERNAL(자체 폼) 정책은 무변경 — 기존 Application(지원) 플로우와 충돌 금지

## 3. 외부 폼 URL 화이트리스트 검증 (FE + BE 동일 정책)

기존 단순 프리픽스 검증(`^https?://`)을 **제거**하고 화이트리스트로 교체:

| 플랫폼 | 허용 호스트 | 추가 조건 |
|---|---|---|
| Google Forms | `forms.gle` | — |
| Google Forms | `docs.google.com` | path 가 `/forms` 로 **시작(startsWith)** — `/forms/u/0/`·`/forms/d/e/` 등 하위 경로 포함 |
| Naver Form | `form.naver.com` | — |

- **HTTPS 만 허용** (http 거부 — 기존 검증은 http 허용이었음)
- URI 파싱 기반 **호스트 정확 일치** (부분 문자열·endsWith 금지 — `docs.google.com.evil.com` 차단)
- 그 외 도메인·단축 URL(naver.me 포함) 거부 — 에러 문구에 허용 플랫폼 안내
- 화이트리스트는 상수 목록으로 두어 추후 플랫폼 추가가 1줄이 되게 한다
- FE(zod)와 BE 가 같은 목록 — 이름 금칙어 전례처럼 **양쪽 동기화 가드 테스트** 필수
- 기존 저장된 URL 은 소급하지 않는다(신규 생성·수정만 검증). `externalFormUrl` 은 생성 후 변경 불가 필드라 실질 영향은 신규 생성뿐

## 4. 가입 코드 — Recruitment 귀속 전환

### 4.1 도메인 변경

- `club_join_code` 는 이미 `recruitment_id`(NOT NULL) 를 가진다 — **귀속의 SoT 를 recruitment 로 승격**
- 활성 1개 제약: `(club_id) WHERE revoked_at IS NULL` → **`(recruitment_id) WHERE revoked_at IS NULL AND deleted_at IS NULL`** 로 교체 (V99 마이그레이션 — 인덱스 drop/create)
  - 동아리에 CLOSED EXTERNAL 모집이 여럿이면 모집별로 각각 활성 코드 1개 가능
- `club_id` 컬럼은 유지(비정규화 — 요청 콘솔·권한 대조 조회 편의)
- 재생성(폐기+신규)·인원 1~500·기수 지정·`used_count`(신청 시 차감·거절 환급) 정책은 v1 유지.
  절대 만료(7/30/90일)는 **가입 가능 기간 프리셋(§4.3)으로 대체** — `expires_at` 대신
  `join_window_days`(0/7/14) 저장, `recruitment.closed_at` 기준 파생 판정
- **감사(Audit) 추적 — 이벤트 단위(최종)**: 신규 테이블 `club_audit_event`(RLS 필수 — 동아리 단위 운영 감사로 범용화, 이번엔 가입 링크 6종만 기록·향후 이벤트 타입 확장) 에
  6종 이벤트를 트랜잭션 내 기록 — `JOIN_LINK_CREATED / JOIN_LINK_REGENERATED / JOIN_LINK_REVOKED /
  JOIN_REQUEST_CREATED / JOIN_REQUEST_APPROVED / JOIN_REQUEST_REJECTED`
  (컬럼: recruitment_id·club_id·join_code_id·join_request_id nullable·event_type·actor_user_id·created_at).
  행 기반 유도(코드 행·JoinRequest 행)로도 추적 가능하지만 명시적 이벤트 스트림 요구를 수용 —
  `created_by`/`revoked_by` 컬럼은 화면 표시용으로 병존. 조회 UI 노출은 후속(우선 데이터 축적).
  REGENERATED 판별: 재생성 트랜잭션(기존 활성 폐기+신규 생성)에서는 CREATED 대신 REGENERATED 1건
  + 구 링크 REVOKED 1건을 기록

### 4.2 생성 조건 (최종 확정 — "가입 링크")

**최초 생성·재생성 모두** `applicationMode == EXTERNAL` **AND** **실질 진행 중(`isEffectivelyOpen` — status OPEN 이고 endDate 미경과)** 일 때만 가능(지원서 제출과 동일 기준 — endDate 경과+미마감 모집 발급 차단).
CLOSED 이후에는 생성·재생성 불가("모집 생성 → 즉시 종료 → 링크만 발급" 우회 원천 차단).

| mode | 상태 | 생성/재생성 |
|---|---|---|
| INTERNAL | (무관) | ❌ 409 ("외부 폼 모집에서만 가입 링크를 사용할 수 있습니다.") |
| EXTERNAL | OPEN·endDate 미경과 (실질 진행 중) | ✅ |
| EXTERNAL | OPEN·endDate 경과 (방치) | ❌ 409 ("모집이 진행 중일 때만 가입 링크를 만들 수 있습니다.") |
| EXTERNAL | CLOSED | ❌ 409 (동일) |

### 4.3 가입 가능 기간 (기존 절대 만료 7/30/90 을 완전 대체)

- 생성 시 프리셋 3택: **모집 종료일까지(0일) / 모집 종료 후 7일(기본) / 모집 종료 후 14일**.
  직접 날짜 입력 없음, 14일 초과 불가(장기 링크 유지 우회 방지). 재생성 시 재선택 가능.
- **기준 시각 = 실제 종료 시각(`recruitment.closed_at`)**, 설정 마감일(endDate) 아님 —
  조기 종료·상시모집·기간 연장을 예외 없이 처리하고 "종료 후 7일"이라는 사용자 기대와 일치.
- 사용 판정: **모집 OPEN 이면 유효** ‖ **CLOSED 이면 `closed_at + 프리셋` 이내에만 유효**.
  (+ 기존 미폐기·미소진·동아리 ACTIVE 게이트 유지, 사유는 학생에게 비구분 단일 안내)
- `closed_at` 은 모든 종료 전이 경로(수동 마감·자동 마감·새 모집 생성 시 기존 OPEN 일괄 마감)에서
  스탬프한다. CLOSED 인데 스탬프가 없는 비정상 데이터는 **사용 불가(fail-closed)**.
  재개 경로가 존재하면 재개 시 closed_at 초기화.
- **상시모집**: 종료 시점이 없으므로 OPEN 동안 링크가 계속 유효, 종료하면 그 시점부터 프리셋 적용.
  상시모집 중 유출은 폐기+재생성(OPEN 이므로 가능)으로 대응.
- 운영자 화면 만료 표시: OPEN 동안은 "모집 종료 후 N일까지" 텍스트, CLOSED 후에는 구체 일시.
- 이미 접수된 PENDING 요청의 **승인/거절은 가입 기간 만료 후에도 가능**(자동 만료 = 신규 요청 차단).
- 발급·삭제의 모집 행 잠금 직렬화는 심층 방어로 유지.

### 4.3.1 폐기 정책

폐기는 언제든 가능(유출 대응). **모집 종료 후 폐기**는 재생성이 불가하므로 확인 모달에 경고
"⚠️ 모집이 종료되어 새로운 가입 링크를 생성할 수 없습니다. 현재 링크를 폐기하면 남아있는 합격자도
가입할 수 없게 됩니다. 정말 폐기하시겠습니까?" + **2단계 확인(타이핑)**: "계속하려면 '폐기' 를
입력하세요" 입력이 일치할 때만 진행(GitHub 브랜치 삭제 방식 — `window.prompt` 금지 전례에 따라
모달 내 인라인 입력). OPEN 중 폐기는 재생성 가능하므로 기존 단일 확인 모달 유지.
- **모집 삭제 정책(신규 — 단계적)**: EXTERNAL 모집은 지원자가 없어 기존 "CLOSED+무지원자" 삭제 조건을
  항상 통과하므로, 가입 코드·요청 상태에 따라 다음과 같이 판정한다:
  | 상태 | 삭제 | 근거 |
  |---|---|---|
  | 가입 코드만 존재 (요청 0건) | ✅ 허용 + **삭제 트랜잭션에서 활성 코드 자동 폐기** | 코드는 모집의 부속물 — 폐기하면 고아 코드로 학생이 유입될 수 없다. 코드 존재만으로 영구 삭제 불가는 과한 제약 |
  | **PENDING 가입 요청 존재** | ❌ 409 "처리되지 않은 가입 요청이 있습니다. 먼저 승인하거나 거절해주세요." | 진행 중인 업무 — 학생이 이미 슬롯을 차감하고 응답을 기다리는 상태다. 삭제로 응답 경로를 없애면 안 되고, 운영진은 일괄 거절 후 삭제할 수 있다 |
  | APPROVED/REJECTED 이력만 존재 | ✅ 허용 + 활성 코드 자동 폐기 | 완결된 감사 이력 — 모집은 soft delete 라 코드·요청 행은 물리적으로 보존되고, 요청 콘솔은 club 단위 조회(모집 미참조)라 이력 열람도 유지된다 |
  - 감사 보존: `club_join_code`·`club_join_request` 행은 모집 삭제와 무관하게 영구 보존(물리 삭제 없음)

### 4.3 API

- 코드 생성/조회/폐기를 **recruitment 스코프**로 이동:
  - `POST /api/v1/clubs/{clubId}/recruitments/{recruitmentId}/join-codes` (201, 조건 미충족 409)
  - `GET  /api/v1/clubs/{clubId}/recruitments/{recruitmentId}/join-codes/active` (200, 없으면 data null)
  - `DELETE /api/v1/clubs/{clubId}/recruitments/{recruitmentId}/join-codes/{joinCodeId}` (204, 멱등)
  - clubId↔recruitmentId 소속 대조(불일치 404), requireManager, Security 매처 갱신(비로그인 401)
- 클럽 단위 구 경로(`/clubs/{clubId}/join-codes*`)는 **제거** (v1 은 미출시 develop 전용이라 하위호환 불요)
- 학생측(`GET/POST /join-codes/{code}*`)·가입 요청 승인측 API 는 경로 무변경 (내부 판정만 §4.2 반영)

## 5. 모집 관리 화면 — 회원 등록 영역

모집 관리(해당 모집 상세)에서, 모드·상태에 따라:

- **INTERNAL**: 가입 코드 관련 UI 를 일절 표시하지 않는다
- **EXTERNAL**: **회원 등록 영역** 표시 — 가입 코드 생성/관리(활성 코드 카드·재생성·폐기),
  가입 요청 관리 진입(기존 `/manage/clubs/{clubId}/members/requests` 링크 + 대기 수 배지),
  §7.1 운영 정책 안내. CLOSED 면 생성 폼 대신 "모집이 진행 중일 때만 가입 코드를 만들 수 있습니다." 안내
  (기존 코드 카드는 사용 불가 표시로 유지 — 승인/거절 링크는 계속 제공)

### 5.1 모집 관리 목록 — 카드 액션 분기·동선 단축

모집 관리(목록) 화면의 모집 카드 액션을 타입별로 분기한다:

- **INTERNAL**: 기존 유지 — [지원자 관리] [통계]
- **EXTERNAL**: [가입 코드] [가입 요청 관리] — 지원자 관리·통계 버튼 제거(외부 폼은 지원서·통계 미사용)
  - [가입 링크] → **카드에서 바로 링크 관리 다이얼로그**(생성[프리셋 §4.3 라디오]·활성 카드·재생성·폐기·
    §7.1 안내·§9 경고·**합격 안내 문구 복사**) — 상세 진입 없이 최다 빈도 작업 완결.
    상세의 회원 등록 영역과 같은 컴포넌트 재사용. QR 은 후속 검토
  - 합격 안내 문구 템플릿(복사 버튼): "🎉 축하드립니다! {동아리명} 최종 합격을 축하드립니다.
    아래 링크를 통해 동아리 가입을 완료해 주세요. 가입은 최초 1회만 필요하며, 가입 완료 후
    정식 회원으로 등록됩니다. {가입 링크}"
  - [가입 요청 관리] → `/manage/clubs/{clubId}/members/requests` (대기 수 배지)
- EXTERNAL 모집 **상세**의 [지원자 관리]·[통계] 링크도 동일 기준으로 제거
- **모집 상세 헤더 배지**: EXTERNAL 모집은 상단에 "외부 폼 모집" 배지 + 플랫폼명(URL 호스트로 판별 —
  forms.gle/docs.google.com → "Google Forms", form.naver.com → "Naver Form") 표시
- 기존 **회원 관리 페이지의 회원 초대 UI 는 구조를 유지**하되, 코드 생성 기능 대신
  "외부 폼 모집의 회원 등록은 모집 관리에서 진행합니다." 안내(+ 모집 관리 이동 링크)로 대체한다 —
  향후 이메일/QR/관리자 직접 초대가 이 자리에 추가될 수 있도록 진입점 구조는 남긴다
  (가입 요청 화면 자체는 클럽 단위 유지 — 요청 목록에 코드·기수가 표시되므로 모집 구분 가능)

## 6. 학생측 — "합격 후 동아리 가입" UX

가입 요청 생성·승인/거절/일괄 승인·차감/환급 메커니즘은 v1 그대로. `/join/{code}` 랜딩만
"회원가입"이 아닌 **합격 축하 → 가입** 톤으로 개편한다:

- 진입(유효 링크·요청 가능 상태): "🎉 축하합니다! {동아리명} 최종 합격을 축하드립니다.
  가입은 약 30초 정도 소요됩니다. 가입 신청을 완료하면 운영진 확인 후 정식 회원으로 등록됩니다."
  + **[동아리 가입하기]** 버튼(비로그인은 [로그인하고 가입하기])
- 신청 완료(PENDING): "🎉 가입 신청이 완료되었습니다. 운영진 확인 후 {동아리명} 동아리 회원으로
  등록됩니다." — **즉시 등록 표현("회원으로 등록되었습니다") 금지**(승인 게이트 존재) + 홈 버튼 유지
- 상태 분기 우선순위(이미 가입/대기/재요청 가능/무효)는 기존 유지, 무효 사유 비구분 단일 안내 유지

## 7. 회원 등록 절차 안내 카드 (EXTERNAL 상시 노출)

EXTERNAL 모집 화면(작성 §1.2·관리 §5)에 절차 카드를 항상 표시 (OPEN 정책에 맞춘 순서):

`외부 모집 진행 → 합격자 선정 → 가입 코드 생성·공유 → 학생 가입 요청 → 운영진 승인 → 회원 등록 → 모집 종료`

### 7.1 운영 정책 안내 카드 (가입 링크 화면 상시 노출 — 최종 문안)

- 가입 링크는 모집이 OPEN 상태일 때만 생성 및 재생성할 수 있습니다.
- 모집 종료 후에는 기존 링크만 사용할 수 있습니다.
- 가입 가능 기간이 종료되면 링크는 자동으로 만료됩니다.
- 모집 종료 이후에는 새로운 가입 링크를 생성할 수 없습니다.

(구 5줄 안내는 closed_at 정책 확정으로 낡아 이 4줄로 대체. 유출 경고는 §8 Warning Card 로 별도 유지)

### 7.2 가입 링크 상태 카드 (Status Card)

가입 링크 화면 상단에 상시 표시: 링크 상태(🟢 활성/만료/폐기) · 가입 가능 기간
(OPEN: "모집 종료 후 N일" 텍스트 / CLOSED: 실제 만료 일시 "YYYY-MM-DD HH:mm까지") ·
**누적 가입 신청 수** · **승인 대기 수(PENDING)**. 카운트는 BE 활성 링크 응답에 포함
(FE 클라이언트 합산 금지 — 단일 출처).

## 8. 차감 정책 안내 + 유출 경고

- **가입 코드 생성·관리 화면 공통 안내**: "가입 요청이 생성되는 즉시 사용 가능 인원이 차감됩니다.
  운영진이 가입 요청을 거절하면 자동으로 사용 가능 인원이 복구됩니다. 링크가 외부에 유출될 경우 승인 여부와 관계없이
  가입 요청이 생성된 횟수만큼 사용 가능 인원이 일시적으로 감소할 수 있습니다."
- **복사 버튼 근처 Warning Card**: "⚠️ 가입 코드는 합격자에게만 공유해주세요. 링크가 외부에 유출되면
  제3자가 가입 요청을 생성할 수 있으며, 가입 요청이 생성될 때마다 사용 가능 인원이 일시적으로
  차감됩니다. 잘못 생성된 가입 요청은 운영진이 거절하면 자동으로 복구됩니다."

## 9. 구현 원칙

- 기존 아키텍처·컨벤션·디자인 시스템(shadcn/ui + 현행 토큰) 유지, 모바일·접근성(ARIA·키보드) 유지
- 기존 Application(지원) 정책과 충돌 금지, ClubMember 생성 공통 서비스(`ClubMemberEnrollmentService`) 그대로 사용
- FE/BE 검증 동일 정책(화이트리스트 동기화 가드)

## 10. Out of Scope

- CSV 회원 생성 / CSV 코드 일괄 발급 / 이메일 초대 / QR 이미지
- 모집별 다중 활성 코드 (모집당 1개 유지)
- naver.me 등 단축 URL 허용 (원본 URL 안내로 대응)
- 학생 가입 요청 취소(CANCELED)
- 기존 EXTERNAL 모집 데이터의 URL 소급 검증

## 11. 릴리스 체크 (v1 에서 승계 + 신규)

- v1 미출시 상태에서의 개편이므로 하위호환 부담 없음 (dev DB 의 v1 코드 행은 마이그레이션 전 정리)
- 배포 시 PENDING 데이터 존재하면 used_count 백필 (v1 체크 승계)
- 콘솔·랜딩은 같은 릴리스로 (v1 체크 승계)
